# buddle 양자내성(Post-Quantum) 보안 검토

> 질문: "전체 보안이 양자컴퓨터에도 뚫리지 않을 만한가?"
> 결론: **애플리케이션 계층 암호는 대부분 이미 양자내성이다.** 진짜 양자 취약점은
> TLS 키 교환(RSA/ECDHE)이며, 이는 인프라/배포 계층의 문제다. 정직하게 구분한다.

---

## 양자 알고리즘 두 가지와 영향

| 알고리즘 | 깨는 대상 | 영향 |
|---|---|---|
| **Shor** | 비대칭 암호(RSA, ECC/ECDSA, DH/ECDHE) | **완전 붕괴** — 다항시간에 해독 |
| **Grover** | 대칭 암호·해시(AES, SHA, HMAC) | **제곱근 가속** — 유효 강도 절반(256→128비트). 키만 충분히 길면 안전 |

핵심: **Shor가 위협, Grover는 키 길이로 흡수 가능.**

---

## buddle 스택의 양자 노출 분석

| 구성요소 | 알고리즘 | 유형 | 양자 영향 | 상태 |
|---|---|---|---|---|
| JWT 서명 | HS256 (HMAC-SHA256) | **대칭** | Grover만 → 256비트 키로 128비트 유지 | ✅ 안전(키≥32B 강제) |
| 비밀번호 해시 | argon2id | 메모리-하드 | Grover 제곱근뿐, 메모리 비용이 병렬화 차단 | ✅ 안전 |
| 무결성(기술자/지식공간) | HMAC-SHA256 | **대칭** | Grover만 → 256비트로 안전 | ✅ 안전 |
| API 키(에이전트) | argon2 해시 저장 | 메모리-하드 | 위와 동일 | ✅ 안전 |
| 토큰 저장(프론트) | 메모리 전용 | — | 암호 무관 | ✅ |
| **TLS(전송)** | RSA/ECDHE 키 교환 | **비대칭** | **Shor에 취약** | ⚠️ 인프라 계층 |

→ **애플리케이션이 직접 쓰는 암호(JWT·비밀번호·HMAC)는 전부 대칭/메모리-하드라 양자내성.** 우리가 RSA/ECDSA 서명 JWT(RS256/ES256)를 안 쓴 게 오히려 다행이다 — HS256은 양자 시대에 더 안전한 선택.

---

## 적용한 수정 (애플리케이션 계층)

### 1. 대칭 키 길이 = 양자 안전 하한 명시
JWT·HMAC 비밀키 ≥32바이트(256비트) 강제 유지하고, 근거를 코드 주석화:
> Grover가 256→128비트로 절반화해도 128비트는 양자 시대에도 안전. 권장은 base64(32바이트)=44자.

이미 `config._reject_dev_secrets_in_prod`가 프로덕션에서 <32자를 거부. 양자 관점 주석 추가.

### 2. "Harvest now, decrypt later" 대비 (가장 현실적 위협)
공격자가 **지금 TLS 트래픽을 수집해 두었다가 미래 양자컴퓨터로 해독**하는 시나리오. 대응:
- 민감 데이터의 수명을 짧게: access token 단수명 + refresh 회전(이미 구현).
- 토큰을 디스크에 안 남김(프론트 메모리 전용, 이미 구현) → 수집 표면 축소.

## 인프라 계층 권고 (코드 아님, 배포 시)

진짜 양자 대비는 전송 계층에서 이뤄진다:

1. **PQC 하이브리드 TLS**: TLS 1.3 + `X25519MLKEM768`(ML-KEM/Kyber 하이브리드 키교환). 2024~2025년 주요 브라우저·CDN·로드밸런서가 지원 시작. → 리버스 프록시(nginx/Cloudflare/ALB)에서 활성화.
2. **인증서**: 현재 RSA/ECDSA 인증서는 서명용이라 "지금 위조"는 양자컴 실물 등장 전엔 불가. NIST PQC 서명(ML-DSA/Dilithium) 인증서가 보급되면 전환.
3. **HSTS 강제**: 다운그레이드 차단(security_headers에 포함 권고).

→ buddle 애플리케이션 코드는 PQC 키교환에 의존하지 않으며, 프록시 계층 교체만으로 양자내성 전송을 얻는다. **앱 재작성 불필요.**

---

## 정직한 결론

- **과장 금지**: "앱이 양자컴퓨터를 막는다"고 말하지 않는다. 앱이 쓰는 *대칭 암호*가 양자내성이고, *전송 보안*은 인프라가 PQC TLS로 담당한다.
- **현재 상태**: 애플리케이션 계층은 양자 시대에도 견디도록 설계됨(HS256/argon2id/HMAC-SHA256 + 256비트 키). 비대칭 암호를 앱 로직에 안 쓴 것이 강점.
- **남은 일**: 배포 시 PQC 하이브리드 TLS 활성화(인프라). 코드 변경 없음.

| 계층 | 양자내성 | 담당 |
|---|---|---|
| 비밀번호/토큰/무결성 | ✅ 예 | 앱(완료) |
| 전송(TLS) | ⚠️ PQC TLS 필요 | 인프라(배포 시) |
| 프론트 공격면 | ✅ XSS/토큰/CSP (SECURITY_FRONTEND.md) | 앱(완료) |
